# SYRIX Forma — Threat Model (started Phase 0, complete by Phase 9)

Status: draft, started per the build plan Phase 0. Each entry gets a real mitigation as the
relevant phase ships — this file must be finalized and reviewed against the actual shipped
architecture before Phase 9 sign-off (the build plan Phase 9 "Done when").

| Threat | Description | Mitigation (phase) | Status |
|---|---|---|---|
| Compromised employee account | Credential theft/phishing gives an attacker a real employee's session | Clerk sign-in + TOTP MFA (Phase 1), audit log (Phase 1) | Partially implemented — MFA (`lib/auth/{mfa-crypto,mfa-keys,totp}.ts`) and audit log (`lib/permissions/audit.ts`) live; no idle/absolute session-timeout policy beyond Clerk's own defaults |
| Compromised device | Employee's laptop/phone is compromised while a session is active | Idle + absolute session timeout (Phase 1), "log out everywhere" (Phase 1), suspicious-session detection (Phase 9) | Partially implemented — "log out everywhere" ships (`features/profile/components/sign-out-other-sessions-button.tsx`); no custom idle/absolute timeout configured; suspicious-session detection is Phase 9 |
| Malicious employee | An authorized user abuses legitimate access | Resource+action-level permissions (Phase 1), audit log (Phase 1), step-up auth for sensitive actions (Phase 5) | Partially implemented — Employee/Task/Client/Project permission predicates + audit log live; step-up auth (`lib/permissions/step-up.ts`) now gates the automation kill-switch/config, granting permissions, admin changes, and enquiry email replies with a fresh TOTP code; no export feature exists yet to gate |
| Stolen session | Session token exfiltrated (e.g. XSS, malicious extension) | HttpOnly/Secure/SameSite cookies (Phase 1), rotation on privilege change (Phase 1), active-session visibility (Phase 9) | Partially implemented — cookie flags are Clerk defaults, not independently verified against this app's config; rotation-on-privilege-change unverified; active-session visibility is Phase 9 |
| Compromised integration | A connected external system (Calendar/Mail/M365) is itself compromised or returns malicious data | Reference-only storage, degrade-independently design (Phase 4), webhook verification (Phase 4) | Partially implemented — Hostinger Mail and the Microsoft 365/SharePoint/OneDrive/NAS document-link integration ship this session, each independently on/off (`integrations.enabled`, checked before every use) and each failing without taking down the rest of the Hub (a failed Hostinger sync only degrades Email/Enquiry email features; a broken document link only flips that one link's status). Credentials are encrypted at rest (`lib/integrations/crypto.ts`), never logged. Google Calendar is not yet built — deferred this session, no `integrations` row seeded for it |
| Malicious document/email | An inbound email or document contains an exploit or a prompt-injection payload | Untrusted-content handling (Phase 4 email intake, Phase 7 SYRIX AI), no privileged action without human approval (Section 12) | Not yet implemented — Phase 4 / SYRIX AI (built last, after Phase 9) |
| Vulnerable dependency | A locked dependency has a known CVE | Dependency scanning in CI (Phase 2+), `DEPENDENCIES.md` tracking | Implemented — `npm audit` + OSV-Scanner in `.github/workflows/ci.yml`, findings tracked in `DEPENDENCIES.md` |
| Compromised third-party package | A dependency is compromised post-install (supply-chain attack) | Dependency/secret scanning + SAST in CI (Phase 2+), pinned versions | Implemented — gitleaks + Semgrep OSS in CI alongside the scans above |
| AI prompt injection | Content the AI reads instructs it to take an unauthorized action | Ephemeral chat, untrusted-content treatment, no standing data access, human approval required for privileged actions (SYRIX AI) | Not yet implemented — SYRIX AI is built last, after Phase 9 |
| Browser-to-AI leakage | Content from an untrusted web page reaches the AI without the user intending it | BLUE/YELLOW/RED isolation states in the in-app browser (Phase 8) | Not yet implemented — Phase 8 |
| Privilege escalation | A lower-role user gains higher-role access via a bug or a crafted request | Server-side permission checks only, tested via authorization tests (Phase 1+) | Implemented and tested — `lib/permissions/{task,client,project}-access.ts` mirror the Employee pattern; cross-resource authorization tests included in the 103-test suite |
| Data exfiltration | Bulk export or scraping of confidential/highly-confidential data | Export approval step-up (Phase 5), audit logging, rate limiting | Partially implemented — audit logging live; no export feature exists yet to gate; general endpoint rate limiting unverified beyond the MFA challenge's own 5-attempt/15-minute lockout |
| Webhook spoofing | A forged webhook call impersonates a real integration event | Webhook signature verification + periodic reconciliation (Phase 4) | Partially implemented — `/api/webhooks/hostinger-mail` verifies the per-webhook bearer token (constant-time comparison, `lib/integrations/hostinger-mail/webhook.ts`'s `verifyWebhookAuthorization`) before processing anything, returns 404 (not 401) if the integration isn't configured so a probe learns nothing, and a 15-minute reconciliation pass (`runHostingerMailReconciliation`) independently re-derives the same state from the mailbox's own search API — a forged or dropped webhook delivery can't create a false enquiry or silently lose a real one. Existing Clerk `user.created` webhook uses Clerk's own signature verification (`verifyWebhook`), unchanged this session. Google Calendar's webhook verification is not yet implemented — deferred this session |
| Malicious chat attachment | An employee (or a compromised account) uploads a file crafted to exploit whoever opens it (malicious PDF/image, disguised executable) | MIME/extension allow-list + size cap enforced server-side (not just client-side), never executing/previewing attachment content server-side, presigned-URL upload flow that never routes file bytes through the Next.js server | Implemented with Team Chat — `features/chat/utils/schemas.ts`'s allow-list (PDF/common images/office docs), rejected server-side even if a client is bypassed; attachments are served back only as opaque downloads via a fresh presigned GET, never rendered/executed by the server |
| Chat attachment URL guessing | An attacker enumerates/guesses a storage key to read another conversation's file without being a participant | Presigned, time-limited GET URLs issued only after `isConversationParticipant` passes — never a permanent/public bucket URL | Implemented with Team Chat — `lib/storage/r2.ts`'s `getSignedUrl` is only ever called from a server action that has already re-checked participancy; the R2 bucket itself has no public read access |
| Chat as a data-exfiltration channel | An employee uses DM/group chat to move confidential data outside their normal access scope | Chat inherits no elevated visibility — access is participant-only (`docs/permissions-matrix.md`), same audit-logging discipline as everything else (conversation-created events logged, message bodies never logged) | Partially implemented — participant gating ships with Team Chat; there is no content-scanning/DLP layer, and none is planned pre-Phase-9 |

This table is the seed set required by the build plan Phase 0 — add rows as new attack
surface appears (new integration, new AI capability, new external-facing endpoint), don't
treat it as closed. Task/Client/Project don't need their own dedicated rows: the existing
"Privilege escalation" and "Malicious employee" rows already cover them generically through
the shared server-side permission-predicate pattern in `lib/permissions/` — a resource-specific
row would only be needed if one of them required a genuinely different threat or mitigation.
